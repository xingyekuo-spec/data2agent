> 状态：**功能已实现，待 Windows 便携包现场验收** · 审核/实现基线：2026-08-08

## 1. 目标与结论

当前中间机管理界面已经覆盖首次配置、ERP 测连、元数据扫描、抽取计划、运行记录、
推送记录、错误处理和日志查看，基本业务流程可以闭环。主要缺口不在视觉风格，而在
“无人值守运维”能力：后台已有的真实进程状态、自动重启和对账调度没有完整呈现，
维护备份结果也没有形成可查询状态；部分请求失败还可能被页面误显示成空数据。

优化目标：

1. 运维人员打开首页后，10 秒内能够判断 launcher、connector、maintenance、ERP、平台和最近同步是否健康。
2. 页面不得把认证失败、接口失败、心跳过期或进程停止显示成“无配置”“暂无记录”或正常计划状态。
3. 所有会影响长期运行的配置都能在页面中查看；允许编辑的字段经过服务端校验和 revision 乐观锁。
4. 所有后台动作都有明确的开始、执行中、完成、失败、是否自动重启以及后续处理提示。
5. 中间机断网、平台不可达或无人操作时，页面仍能给出可信的本机状态和恢复指引。
6. 页面和生产启动检查必须明确证明“中间机仅持久化控制状态、不持久化业务 Raw”；任何
   `sink: local`、本地 Raw 表或未受控临时 spool 都按生产阻断故障处理。

实现依据：[`middle/maintenance/__main__.py`](../../data2agent/middle/maintenance/__main__.py)。

生产 `sink.type: http` 模式下，这个 SQLite 是中间机**控制状态库**：只保存水位、审计、
运行步骤和推送记录，不允许存在 `raw_*` 业务表。迁移已经完成：新配置和新安装使用
`state_db` 与 `middle-state.sqlite`；旧 `landing` 键只在读取时兼容，若与 `state_db` 冲突则拒绝
加载。内部存储类暂保留历史名称 `LandingStore`，不影响对外配置、页面和运维语义。

#### 3.2.1 控制状态库与备份内容边界

| 优化项 | 设计约束 | 页面/运维要求 | 验收方式 |
| --- | --- | --- | --- |
| 明确 SQLite 定位 | SQLite 只作为业务链路的控制面状态库，不作为 ERP 数据副本或查询库 | 所有页面统一称为“中间机状态库”，不得使用“本地业务库”“数据备份”等易误解文案 | 页面、配置和恢复文档中不得将状态库描述成业务落地库 |
| 最小化持久化内容 | 允许保存增量水位、同步运行/步骤、推送批次、generation/回执、对账与必要审计状态；禁止保存 ERP 原始行、字段值快照、完整 SQL、DSN、Token 和密码 | 状态接口只返回计数、状态码和脱敏摘要，不提供状态库下载或任意 SQL 浏览入口 | 自动化检查无 `raw_*` 表、API 不回显 secrets；抽样检查控制记录不含业务行载荷 |
| 区分状态库备份与节点灾备 | SQLite 备份只覆盖上述控制状态；配置、secrets、程序、日志、证书和平台端 Raw 数据均不在其中 | 最近备份卡片固定显示“不含业务 Raw”，恢复页分别列出“会恢复”和“不会恢复”内容 | 执行离线恢复后水位/运行状态可读，配置和平台 Raw 不被覆盖 |
| 控制增长与保留 | 运行、步骤和推送审计按保留期清理，回执采用单独保留期，备份按份数轮换；清理失败不能伪装成维护成功 | 展示已清理数量、当前备份数、数据库/备份大小、最近成功和最近失败 | 连续运行及失败注入后，大小受控且 `last_attempt`/`last_success` 语义正确 |
| 文件敏感性与访问控制 | 状态库虽无业务 Raw，仍含表名、source、水位和错误摘要，应按内部敏感运维数据保护 | 管理页只显示脱敏文件名；状态库和备份目录仅允许运行账户/管理员访问，若使用加密卷须保留现场证据 | Windows ACL、备份目录权限和静态加密属性纳入部署验收记录 |
| 恢复安全 | 禁止在进程运行期间直接覆盖 SQLite；恢复前停服务、校验备份完整性并保留当前库回退副本 | 仅提供只读说明和 runbook 链接，不提供无确认的一键覆盖按钮 | 恢复演练包含停服、完整性检查、回退和恢复后 readiness 检查 |

因此，“中间机不落地数据”的准确表述是：**不持久化 ERP 业务 Raw，但会持久化保障断点续传、
幂等推送和故障恢复所必需的最小控制状态**。这些控制状态的备份不能替代 ERP、平台数据库或
整个中间机节点的灾备。

### 3.3 请求错误与登录状态

| ID | 优化项目 | 前端工作 | 后端配套 | 验收标准 |
| --- | --- | --- | --- | --- |
| MUI-P0-11 | 统一检查 HTTP 状态 | 所有 `fetch`/HTMX 请求先判断状态码，再解析业务数据 | API 继续返回统一错误结构 | 401、403、409、500、超时不得显示成空列表或“无源配置” |
| MUI-P0-12 | Token 失效处理 | 401 时清理无效会话、显示登录页，并在登录后返回原页面 | 可增加轻量认证校验接口，或直接以受保护 API 校验 | 输入错误 Token 后有明确提示，不进入伪正常页面 |
| MUI-P0-13 | 退出与重新登录 | 顶栏提供退出；支持在不清浏览器数据的情况下更换管理密码 | 无额外依赖 | 退出后 session Token 被清除，受保护数据不再显示 |
| MUI-P0-14 | 网络/API 故障状态 | 页面显示“管理 API 不可达/请求超时/最近成功刷新时间” | 统一错误码和建议字段 | 拔网或停止 API 后保留最后成功时间，但旧数据明确标记为过期 |
| MUI-P0-15 | 禁止失败静默降级 | 摘要、告警、状态、日志加载失败均使用错误态和重试按钮 | 无额外依赖 | 任何主要卡片只有加载、成功、空数据、失败四种明确状态 |

上述风险已通过共享 [`admin.js`](../../data2agent/shared/admin_templates/static/admin.js) 收口：页面不再
直接调用 `fetch`，统一处理超时、非 JSON、HTTP 错误和 401；Token 仅保存在当前标签页的
`sessionStorage`，退出或 401 会清除并回到登录面板。状态和告警轮询在页面隐藏时降频，连续失败
指数退避，恢复后自动刷新并提示。

### 3.5 无 Raw 落地边界与临时数据安全

| ID | 优化项目 | 前端工作 | 后端/运行时配套 | 验收标准 |
| --- | --- | --- | --- | --- |
| MUI-P0-22 | 状态库语义与命名迁移 | 状态、维护、配置和恢复页面统一使用“中间机状态库”，显示“仅控制状态、不含业务 Raw”说明 | 中间机配置由 `landing` 迁移为 `state_db`，数据库默认名改为 `middle-state.sqlite`；迁移期只读兼容旧字段并给出弃用提示 | 新安装不再出现含义模糊的 `landing/factory.sqlite`；旧配置可安全迁移；API 和页面不把状态库称为业务落地库 |
| MUI-P0-23 | 生产 HTTP sink 强制 | 配置页在生产模式只展示平台推送配置；若读到 `sink: local`，显示阻断告警且不得显示部署就绪 | 便携包构建、首次配置、readiness 和 connector 启动共同拒绝生产 `sink.type != http`；`local` 仅允许显式开发/测试模式 | 修改生产配置为 `local` 后 connector 拒绝启动、readiness 失败且页面出现严重告警；不得在中间机创建 Raw 表 |
| MUI-P0-24 | Raw 表不变量检查 | 首页和首次部署检查显示“本机 Raw 表：0”；发现 Raw 表时显示不可静默的严重数据驻留告警，只展示表数量和脱敏名称摘要 | 状态 API 只读检查状态库 `sqlite_master`，输出稳定错误码 `middle_raw_persistence_detected`；不得查询或回传 Raw 行内容 | HTTP 模式正常运行后 `raw_*` 表数量始终为 0；注入测试 Raw 表后 15 秒内告警且 readiness 失败 |
| MUI-P0-25 | 全量 spool 数据驻留策略 | 配置/状态页显示当前策略、临时目录是否受保护、是否存在活跃或遗留 spool；严格无落盘场景明确显示“磁盘 spool 已禁用” | 提供明确策略：受控加密临时卷 spool，或严格模式下取消磁盘 spool 并采用经评估的流式方案；设置最小目录权限、启动时遗留清理、异常退出清理和磁盘阈值 | 未配置策略时生产 readiness 失败；严格模式测试不得产生业务数据临时文件；加密 spool 模式须验证目录权限、加密前提、崩溃恢复与遗留清理 |

这里的“不落地”专指**业务 Raw 不持久化到中间机**，不等于中间机完全无状态。水位和运行
状态必须跨进程重启持久化，否则断电后无法安全续传。生产新安装默认使用 `strict_stream`：
`full_refresh` 不创建业务数据临时文件，但网络推送期间会继续持有 ERP 读取游标，须在真实 ERP
上验证快照时长与并发影响。若现场选择 `encrypted_temp_volume`，必须使用已验证静态加密的专用
卷；程序负责最小文件权限、按 source 清理遗留文件和异常退出清理，但不会把“配置声明已加密”
当成操作系统卷加密的替代证据。旧 `temporary_file` 策略仅允许开发/测试模式。

实现依据：[`middle/extract/increment.py`](../../data2agent/middle/extract/increment.py)、
[`middle/extract/sink.py`](../../data2agent/middle/extract/sink.py)、
[`shared/config.py`](../../data2agent/shared/config.py)。

## 6. 已落地的 API 与状态模型

为避免页面通过日志文本或多个接口猜测状态，`/api/status` 已按下列结构扩展（示意字段）：

```json
{
  "observed_at": "2026-08-07T10:30:00+08:00",
  "status_ttl_seconds": 15,
  "process_status": {
    "supervised": true,
    "stale": false,
    "launcher_pid": 1234,
    "processes": [
      {
        "name": "connector",
        "pid": 1235,
        "state": "running",
        "restarts": 1,
        "last_exit_code": null,
        "loaded_config_revision": "sha256:..."
      }
    ]
  },
  "maintenance": {
    "backup_kind": "middle_state",
    "last_attempt_at": "2026-08-07T02:00:00+08:00",
    "last_success_at": "2026-08-07T02:00:05+08:00",
    "backup_file": "middle-state-20260807-020000.sqlite",
    "integrity": "ok",
    "backup_age_seconds": 30595,
    "free_gb": 48.2,
    "min_free_gb": 2.0,
    "error_code": null
  },
  "data_residency": {
    "sink_type": "http",
    "state_db_kind": "middle_state",
    "raw_table_count": 0,
    "spool_policy": "encrypted_temp_volume",
    "spool_active": false,
    "orphan_spool_count": 0,
    "compliant": true,
    "error_code": null
  },
  "readiness": {
    "ready": true,
    "checks": []
  },
  "sources": []
}
```

约束：

- 状态由服务端给出 `observed_at`、TTL 和稳定状态码，浏览器只负责显示。
- 路径、Token、DSN、用户名和 SQL 内容必须脱敏；状态接口不得回显 secrets。
- “未知”必须作为独立状态，不能默认映射为健康。
- 推算值必须带 `derived: true` 或等价标识，不能与实际调度器/执行记录混淆。
- maintenance 状态文件采用临时文件 + 原子替换，读取失败保留明确错误而非空对象。
- `data_residency` 只返回模式、计数、合规结论和脱敏摘要，不读取或返回任何 Raw 行内容。
- `raw_table_count > 0`、生产 `sink_type != http` 或 spool 策略未验收时，`readiness.ready`
  必须为 `false`，不能由前端自行降级成警告。

## 8. 推荐实施顺序

1. **统一请求与认证错误处理**：先消除“错误显示为空数据”的误导。
2. **真实进程健康与全局横幅**：消费现有 `process_status`，建立可信首页。
3. **状态库语义与数据驻留护栏**：完成命名迁移、生产 HTTP sink 强制、Raw 表不变量和 spool 策略。
4. **维护结果持久化与状态 API**：补齐状态库备份、磁盘和清理可观测性。
5. **对账配置与状态**：补齐已存在后端能力的配置入口和运行结果。
6. **统一重启语义与配置 revision 生效状态**：让保存后的行为可验证。
7. **generation、回执、对账详情**：增强跨机推送排障能力。
8. **高级连接参数、告警模型与诊断摘要**：降低现场维护成本。
9. **响应式、可访问性、CSP 和完整 E2E**：完成质量收口。

## 9. 生产验收门槛

满足以下条件后，中间机管理界面才能作为“无人值守生产运维入口”验收：

- [x] P0 项目全部完成且有自动化测试。
- [ ] 手工终止 connector 后，15 秒内出现全局故障告警，launcher 自动恢复后告警自动关闭并留下事件记录。
- [ ] 停止 launcher 后，状态明确变为过期/不可监管，不显示正常运行。
- [x] Token 错误、API 500 和网络中断不会显示成空数据或健康状态（自动化与 smoke 证据）。
- [x] 每日状态库备份结果、完整性和磁盘余量可见；备份过期或失败会告警，页面明确说明不含业务 Raw。
- [x] 生产配置强制使用 HTTP sink；readiness 显示本机 Raw 表为 0，注入 Raw 表后出现不可静默的阻断告警。
- [x] 默认 `strict_stream` 不写业务临时文件且清理回归通过；若改用加密临时卷，部署方须另附真实卷加密证据。
- [x] L1/深度对账配置可保存、可验证，页面能区分计划与实际结果。
- [x] 配置保存后能明确看到自动重启、人工重启或已加载 revision。
- [ ] 便携包真实 E2E 覆盖首次配置、抽取、推送、generation、重启恢复和维护备份。

## 10. 非目标

- 不把中间机管理界面扩展为平台 Vue Console 的替代品。
- 不在浏览器中提供任意 SQL、任意命令执行或 ERP 写回能力。
- 不在页面中回显、下载或复制 Token、密码、完整 DSN 等 secrets。
- 不提供无确认的在线数据库覆盖恢复操作。
- 不把中间机状态库备份描述为平台业务数据备份或完整节点灾备。
- 不因为加入状态页面而改变现有抽取、推送、generation 和水位事务语义。
