## 1. 目标

把当前“逐对象直接重建 `obj_*`”的发布方式改造成真正的数据集级发布：所有目标对象先写入不可变构建表，完整校验通过后，仅在一个 SQLite 短事务内切换当前 `published` 元数据指针。任何对象失败、熔断、进程中断或发布事务失败，都不得让 MCP、Console 或指标读取到空表、半成品或跨版本混合结果。

M2 完成后必须具备以下能力：

- 同一 source 的全部目标对象作为一个 `dataset_version` 构建和发布；
- 构建期间继续服务上一稳定版本；
- 一次发布对读者表现为“全旧”或“全新”，不存在中间态；
- 仅允许回滚到当前版本的直接上一稳定版本；
- 不同 source 的物理对象表和发布指针相互隔离；
- MCP、Console 数据浏览和指标计算消费同一个已发布快照；
- 模板文件升级后，即使新构建失败，旧稳定版本仍能按其冻结模板继续服务；
- CLI、调度器、Console apply/retry 入口迁移到统一的数据集构建编排，不再旁路写稳定表。

## 2. 当前实现基线与缺口

### 2.1 已具备的 M1 基础

- `d2a_dataset_version` 已记录 source、模板版本、状态、上一版本、错误和冻结对象清单；
- `d2a_object_version` 已记录对象版本、binding 摘要、行数、批次、构建表和状态；
- 数据集/对象状态枚举和“同 source 最多一个 published”约束已经存在；
- datasets 列表/详情 API 已只读开放，publish/rollback 仍以 `501` fail-closed；
- `template_version` 与确定性 `binding_hash` 已有契约和回归测试。

### 2.2 M2 必须消除的旁路

| 位置 | 当前行为 | 风险 | M2 目标 |
| --- | --- | --- | --- |
| `connect/mapping_apply.py` | `apply_object` 直接 DROP/CREATE/INSERT `obj_{Object}` 并提交 | 单对象提交导致跨对象混合版本和读空窗 | 只写不可变候选表，不改变 published 快照 |
| `apply_objects` | 循环对象，某对象熔断不阻止其他对象生效 | 全体发布语义缺失 | 统一候选版本；任一失败则全体不发布 |
| `connect/scheduler.py` | 同步后直接调用旧 `apply_objects` | 调度路径可旁路新发布协议 | 成功构建后自动原子发布 |
| CLI apply/retry | 分别调用旧 `apply_objects`/`apply_object` | retry 可单独替换一个对象 | apply 构建完整数据集；retry 也触发完整重建 |
| Console apply/retry | 同上 | API 与调度语义不一致 | 复用同一数据集编排器 |
| `mcp_server/core.py` | 直接查询无 source、无版本的 `obj_*` | 多源冲突，无法证明实际版本 | 事务内解析 published 快照后查询物理表 |
| `metrics_impl.py` | SQL 固定引用 `obj_*` | 指标可能跨版本/跨来源 | 显式声明依赖并注入已校验物理表名 |
| Console 浏览/概览/可观测 | 多处直接查询 `obj_*` | 页面与 MCP 看到不同发布状态 | 统一使用 published 快照解析器 |

## 3. 固定设计决策

### 3.1 发布模型

采用“不可变物理版本表 + 原子元数据指针”模型，不通过重命名一组共享 `obj_*` 表实现切换。

```text
raw_* / binding / frozen template snapshot
                  │
                  ▼
        build dataset candidate
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
objv_<opaque>_A       objv_<opaque>_B  ...   （不可变）
        │                   │
        └─────────┬─────────┘
                  ▼
       validate full frozen manifest
                  │
                  ▼
 BEGIN IMMEDIATE: retire old metadata → publish candidate metadata
                  │
                  ▼
 MCP / Console / metrics resolve one published snapshot in one read transaction
```

选择这一模型的原因：

1. 发布事务只更新少量元数据行，不在临界区构建、复制、删除或重命名大表；
2. SQLite 读事务天然看到切换前或切换后的完整快照；
3. 物理表带 source 隔离，不再让多个来源争用同一 `obj_*`；
4. 回滚只切元数据，不需要重新构建旧数据；
5. 查询日志能够准确记录实际解析到的 `dataset_version`。

`obj_{Object}` 降级为旧版兼容遗留物，不再是 M2 的发布事实源。不得为已有 `obj_*` 伪造一个数据集版本；M2 升级后的来源在首次真实版本化 apply 成功前，版本化数据读取必须 fail-closed。

### 3.2 数据集成员与冻结内容

候选数据集的 `object_manifest` 定义为：当前模板包中，对指定 source 存在 `enabled` binding 的全部对象，按稳定顺序冻结。

- 无任何启用对象：前置检查失败，返回 `409`；不创建 Run，不创建候选版本；
- 启用 binding 但缺少或清空必需 mapping：整批前置检查/构建失败，不能静默跳过；
- 每个对象冻结当前 `binding_hash`；
- `source`、`template_version`、`object_manifest`、对象的 `binding_hash` 和构建完成后的 `row_count/build_table` 不得被发布/回滚动作改写；只有保留策略回收已退休且不受保护的物理表时，允许把 `build_table` 原子转换为已清理 tombstone；
- 创建候选时冻结当时的当前 published 版本到 `previous_dataset_version`，防止迟到候选覆盖后来已经发布的版本。

### 3.3 冻结模板快照

M2 为 `d2a_dataset_version` 增加内部字段 `template_snapshot`，保存规范化后的完整 `TemplatePack` JSON。它不直接暴露给 datasets API。

这是继续服务旧稳定版本的必要条件：若磁盘模板已经发生破坏性升级，而新数据集构建失败，读取层仍须使用旧 published 数据集自己的对象字段、敏感标记、binding 状态和指标定义，不能拿当前模板解释旧表。

- 每个 M2 新候选必须写入并可严格解析 `template_snapshot`；
- 旧记录允许迁移后该字段为空，但缺少有效快照的记录不可被新发布或回滚；
- 查询服务使用 published 快照中的模板，不使用磁盘当前模板解释已发布数据；
- 模板快照格式损坏时 fail-closed，并只向 API 返回安全错误摘要和 `error_id`。

### 3.4 物理表名与 SQL 安全

物理构建表名由内部代码生成，例如：

```text
objv_<source_digest>_<object_digest>_<version_token>
```

- digest/token 只允许小写 ASCII 十六进制和固定前缀；
- `dataset_version` 可采用 `UTC 时间 + 随机后缀`，但 API 路径中的用户输入永不直接拼入 SQL 标识符；
- 解析器只接受数据库中已记录且通过严格格式校验的 `build_table`；
- 所有动态表名继续使用安全标识符引用；查询参数仍使用参数绑定；
- 同一对象版本的物理表发布后不可变，任何重新构建都产生新表。

## 4. 状态机与不变量

### 4.1 数据集状态

```text
building ──构建失败/中断恢复──> failed
    │
    └──清单完整、全部对象 built──> published
                                      │
                  发布下一版/回滚离开 │
                                      ▼
                                   retired
                                      │
                  仅作为直接上一版本回滚
                                      ▼
                                  published
```

- “已构建待发布”继续使用 `building`；就绪状态由冻结清单完整且所有对象均为 `built` 推导，不新增 `ready` 枚举；
- `built_at` 是构建完成时间，成功后不可变；
- `published_at` 是最近一次激活时间，首次发布和回滚激活时更新；
- `previous_dataset_version` 表示本次激活前的稳定版本，只能由创建候选或原子激活事务写入；
- `failed` 数据集永远不能发布；`retired` 只能通过合法 rollback 恢复。

### 4.2 对象状态

```text
building → built → published → retired
    └──────→ failed              └──rollback──> published
```

一个 published 数据集的冻结清单必须与对象版本行集合完全相等，且所有对象行均为 `published`。任何缺失、额外、损坏、表不存在或行数不匹配都必须拒绝发布/回滚和数据读取。

### 4.3 数据库级不变量

在 M1 约束上补充迁移、索引和触发器：

- 同一 source 最多一个 `building` 候选：仍有关联运行任务的候选使新构建返回 `409`；已完成的 stage-only 候选可由下一次显式构建标记为 `failed/superseded` 后替换；崩溃遗留候选按恢复规则关闭；
- 同一 source 最多一个 `published` 数据集；
- 数据集发布状态与清单对象状态一致；
- 冻结字段创建后不可修改；
- `published`/`retired` 必须有 `published_at`；
- 新候选必须有有效 `template_snapshot`；
- `d2a_object_version` 增加 nullable `purged_at`；只有 retired、非 current/previous 对象版本允许从有效 `build_table` 转换为 `build_table=NULL + purged_at`；
- `d2a_sync_run` 增加 nullable `dataset_version`，并通过外键/应用校验只引用真实版本；
- 新增 `publish`、`rollback` Run 类型和 `dataset` Step 类型，后端契约、OpenAPI 和前端筛选同步更新。

## 5. 核心流程契约

### 5.1 构建候选数据集

建议新增 `data2agent/connect/dataset_publish.py`，集中管理版本 ID、快照解析、整批构建、发布、回滚、恢复和保留策略；`mapping_apply.py` 只保留映射转换与候选表写入职责。

```text
build_dataset(source, auto_publish):
  1. 校验 source、模板和完整 enabled manifest；无成员则 409/失败返回
  2. 在写事务内恢复同 source 陈旧 building 候选
  3. 生成内部 dataset/object version 和安全物理表名
  4. 创建 building 数据集，冻结模板、清单、binding hash、当前 previous
  5. 对清单中每个对象执行纯映射并写入自己的不可变候选表
  6. 写对象版本 built/failed、row_count、batch_id、build_table 和安全错误
  7. 可继续构建其余对象以收集诊断，但任一失败即把数据集标记 failed
  8. 全部成功则保持 building + ready；auto_publish=true 时调用 publish
```

约束：

- 构建不得 DROP/CREATE/INSERT 当前 published 物理表；
- 熔断是数据集失败条件，不能只阻止一个对象；
- 构建错误保留内部诊断，API 继续使用固定摘要 + `error_id`；
- 失败候选的物理表在发布事务外 best-effort 清理，元数据和安全错误保留；
- 清理失败不改变稳定版本，也不把失败候选误标为可发布。

### 5.2 原子发布

`POST /api/datasets/{version}/publish` 中的 `{version}` 表示待激活候选版本。

发布前校验：

1. 版本存在且 source 匹配内部记录；
2. 状态为 `building`；
3. 冻结清单、模板快照可解析；
4. 对象行集合与清单完全一致且全部 `built`；
5. 每张候选表存在、表名合法、实际行数与记录一致；
6. 候选记录的 `previous_dataset_version` 与此刻当前 published 版本相同；
7. 已经是当前 published 的同一版本视为幂等成功，`executed=false`。

短事务算法：

```sql
BEGIN IMMEDIATE;
-- 事务内再次执行全部会受并发影响的校验
UPDATE current dataset/object rows: published -> retired;
UPDATE candidate object rows: built -> published, published_at = now;
UPDATE candidate dataset: building -> published, published_at = now;
UPDATE related Run: dataset_version = candidate;
COMMIT;
```

临界事务内不得创建、填充、删除或扫描对象数据表。任一步异常必须整体回滚，旧版本仍为唯一 published。不存在返回 `404`；失败、残缺、过期候选或非法状态返回 `409`；未预期错误返回安全 `500 + error_id`。

### 5.3 原子回滚

`POST /api/datasets/{version}/rollback` 中的 `{version}` 表示要恢复的 retired 目标版本，不是当前版本。

- 目标必须正好等于当前 published 数据集的 `previous_dataset_version`；
- 只支持直接上一稳定版本，不开放任意历史跳转；
- 目标清单、模板快照、对象行和全部物理表须重新验证；
- 目标已经是当前 published 时幂等返回 `executed=false`；
- 缺失返回 `404`，非直接上一版、已清理或状态非法返回 `409`。

```sql
BEGIN IMMEDIATE;
-- 事务内重验 current、target 和物理表元数据
UPDATE current dataset/object rows: published -> retired;
UPDATE target object rows: retired -> published, published_at = now;
UPDATE target dataset:
  retired -> published,
  previous_dataset_version = version_being_left,
  published_at = now;
COMMIT;
```

更新 `previous_dataset_version` 后，可以对刚才的回滚执行一次反向回滚；同时仍保持“一步回退”的有限语义。响应中的 `dataset_version` 始终是操作后实际激活的版本。

### 5.4 保留、清理与崩溃恢复

- 每个 source 至少保留当前 published 和它的直接 previous 的完整物理表集合；
- 发布/回滚成功后，在临界事务外 best-effort 清理更老 retired 版本的物理表；
- 清理在独立 GC 事务中完成；清理后保留历史元数据，但将对应 `build_table` 置空、写入 `purged_at` 并明确不可回滚；
- 清理失败只记录 warning，由后续 apply/publish 启动时重试，不回滚已经成功的发布；
- 永不清理当前版本和 `current.previous_dataset_version`；
- 新构建启动时检测同 source 陈旧 `building`：标记 failed，清理已创建的孤儿候选表，再创建新候选；
- 进程在物理表创建与元数据更新之间中断时，恢复流程按安全命名前缀识别孤儿表，但只能删除能够证明不属于 current/previous 的表。

## 6. 统一读取快照

新增类型化 `PublishedDatasetSnapshot`，至少包含：

```text
source / dataset_version / template_version / template_pack
object -> object_version / binding_hash / row_count / physical_table
```

所有版本化读取遵循同一顺序：

```text
open read-only connection
BEGIN
resolve and fully validate one published snapshot for source
execute object/metric/console reads using snapshot physical tables
record actual dataset_version in query/run metadata
COMMIT and close
```

元数据解析和数据查询必须位于同一 SQLite 读事务，因此并发发布时只能看到全旧或全新。禁止以下降级：

- 未找到 published 元数据时回退到遗留 `obj_*`；
- 读取当前磁盘模板来解释旧 published 物理表；
- 指标的不同依赖对象分别解析发布版本；
- Console 与 MCP 各自实现一套“当前版本”算法。

对象 catalog 可继续展示当前模板定义；但任何实际对象数据、指标、Overview 健康度、Pipeline 对象层、可观测统计和数据浏览都必须基于 published 快照。raw 浏览仍独立于对象层发布。

### 6.1 指标和 MCP 元数据

- 指标实现显式声明依赖对象集合；
- 构建 SQL 时从同一 snapshot 注入经过校验和引用的物理表名；
- 查询响应元数据增加 `dataset_version`、`template_version`、`binding_hashes`；
- 对象查询的 `binding_hashes` 只有该对象一项，指标查询包含全部依赖对象；
- query log/evidence 入口从 M2 起记录实际 `dataset_version`，M5 在此基础上完善会话证据；
- 无 published 快照、快照损坏或依赖缺失时返回稳定的 `not_published`/安全错误，不泄漏表名、SQL 或内部异常。

## 7. 外部入口和 API 契约

### 7.1 Apply

为 `/api/actions/apply` 增加专用 `ApplyActionBody`：

```text
source: string
publish: boolean = true
```

不修改被 sync/reconcile/retry 共用的通用 `ActionBody`，避免无关接口意外接受发布参数。

- `publish=true`：构建完整候选并在成功后自动发布；
- `publish=false`：只构建 ready 候选，返回版本供后续 publish API 激活；
- `ApplyActionResult` 兼容增加 `dataset_version`、`published`、`previous_dataset_version`；
- CLI `apply` 默认保持“成功即生效”，新增 `--stage-only` 对应 `publish=false`；
- scheduler 固定使用自动发布；
- 构建失败时 `aborted=true`，稳定 published 版本不变。

### 7.2 Retry

单对象 retry 不能再单独替换一张 published 表。CLI quarantine retry 和 Console `/api/actions/retry` 均触发完整数据集重建/自动发布；请求中的 object 只用于前置定位、审计和结果聚焦，不缩小发布清单。

`RetryActionResult` 兼容增加 `dataset_version`。只有完整数据集发布成功，隔离记录才按现有语义更新为已被新版本取代；失败时保留旧 published 快照和可重试状态。

### 7.3 Publish / rollback

`DatasetActionResult` 保持 M1 已冻结字段：

```text
executed / dataset_version / note
```

两接口移除 `501`，补齐 `200/404/409/500` OpenAPI 响应。并发提交通过写事务和状态重验序列化，不依赖进程内锁保证正确性。

### 7.4 Run 与页面语义

- apply Run 指向候选/最终版本；独立 publish、rollback 各创建自己的 Run；
- Pipeline 对象节点同时展示 raw 新鲜度和已发布对象版本：raw 已更新但新构建失败时显示“对象层仍服务旧版本”的 warning/stale，而不是 partial success；
- Overview 的对象统计、最近更新时间和健康度来自 published snapshot；
- `/api/objects` 的版本信息来自 `d2a_object_version`，不能猜测表名；
- datasets 页面/接口明确区分 building-ready、failed、published、retired 及可发布/可回滚原因；
- 前端生成类型、Pinia store、mock fixture 和 E2E 场景同步更新。

## 10. 重点测试矩阵

### 10.1 原子性与并发

- 初次发布：无旧版本时完整候选一次成为唯一 published；
- 多对象中最后一个对象失败：所有旧对象仍可查询，新候选均不可见；
- 在 retire old 后、publish candidate 前注入异常：事务回滚后旧版本仍完整 published；
- rollback 中途注入异常：当前版本和目标版本状态均恢复原样；
- 循环并发读取对象和多对象指标，同时重复发布：每次响应只能属于完整旧版或完整新版；
- 两个并发 publisher：一个成功，另一个因状态/previous 失配幂等或 `409`，不能形成双 published；
- 构建期间发生另一次发布：原候选因 stale previous 被拒绝。

### 10.2 版本隔离与读取

- 两个 source 含同名对象，分别发布后物理表、行数、结果和版本元数据互不串线；
- 同一指标的所有对象依赖来自同一 dataset snapshot；
- 数据库有遗留 `obj_*` 但没有 published 元数据：MCP/Console 对象读取拒绝，不回退；
- 磁盘模板升级且新构建失败：旧 published 的冻结字段、敏感标记和指标仍可查询；
- published 快照的 template JSON、manifest、对象行、表名或表实体损坏：fail-closed；
- 查询返回的 `dataset_version/template_version/binding_hashes` 与实际使用物理表一致。

### 10.3 回滚、保留与恢复

- 首次发布没有 previous，rollback 返回 `409`；
- 发布 V2 后只允许回滚到 V1；请求 V0 或其他 source 版本返回 `409/404`；
- V2 → V1 回滚后可一步恢复 V2；响应版本始终等于当前激活版本；
- 当前与 immediate previous 表永不清理，更老 retired 表最终被清理且元数据仍可审计；
- 清理失败只产生 warning，published 不回退；
- 进程中断遗留 building/孤儿表，下一次构建安全标记 failed 并回收，不误删稳定表。

### 10.4 入口兼容

- CLI apply 默认成功即发布，`--stage-only` 只构建；
- scheduler 同步成功后完整构建并自动发布，失败时继续服务旧版本；
- Console apply 的 `publish=false` 返回可供 publish API 使用的候选版本；
- CLI/Console retry 始终重建完整 manifest，不再单独发布对象；
- quarantine、Run、审计、Overview、Pipeline 和数据浏览既有契约无无关回归；
- `/`、`/v0`、`/v1` 和便携分发检查保持通过。
