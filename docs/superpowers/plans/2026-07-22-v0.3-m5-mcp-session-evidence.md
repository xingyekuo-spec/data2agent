## 1. 目标

把当前进程内、有限容量的 query 日志升级为持久、隔离、可校验的查询证据：

```text
principal + session_id + query_id
+ normalized_query + dataset_version
+ result_digest + result_summary + warnings
+ created_at + expires_at
```

M5 完成后：

- 每次返回业务数据的 `query_objects/query_metrics` 都产生不可预测、重启后仍可核验的 query evidence；
- query evidence 只属于创建它的主体和会话，请求体与 MCP 工具参数不能自行声明主体；
- 建议卡引用 evidence 时必须同时提交 `query_id + result_digest`，并在一个事务中完成归属、有效期、数据集版本和 digest 校验；
- 建议卡永久固化查询时的规范化条件、实际 `dataset_version`、脱敏结果摘要和全部 warnings，不因后续发布、回滚或查询过期而被改写；
- Console 可以读取同会话 query/proposal 详情，MCP Lab 不再依赖浏览器内存中的完整查询结果解释旧建议卡；
- 查询、建议卡和拒绝事件进入 SQLite 持久审计；现有 JSONL 只作为可选兼容输出，不再是唯一证据来源。

本里程碑证明“某主体在某会话中，基于某个已发布数据集版本看到了哪类脱敏结果，并用该结果生成了什么建议”。它不承诺理解自然语言 claim，也不自动判断 claim 中每个数字是否等于查询结果。

## 2. 开始基线与现有缺口

### 2.1 可复用能力

- M1/M2 已提供不可变的 `dataset_version/template_version/binding_hash`，且 MCP 查询在同一只读事务内解析实际 published snapshot；
- `QueryService` 已统一承载 MCP stdio、MCP HTTP 和 Console MCP Lab 的对象/指标查询及建议卡逻辑；
- 查询响应已有 `meta.query_id/tool/target/row_count/warnings/dataset_version/template_version/binding_hashes`；
- 对象敏感字段在 query evidence 生成前已经脱敏，指标 caveat 与 draft warning 已进入响应；
- Console 已有类型化 MCP Lab、建议卡入口、错误模型、Mock 与 Vue `sessionStorage` Token 纪律；
- MCP HTTP 已有单 Token、协议会话和可选 JSONL audit sink，stdio 天然以单个进程连接作为会话边界；
- landing schema 已有幂等迁移、不可变元数据触发器和并发事务测试基础。

### 2.2 必须消除的缺口

- `_query_log` 只存在于单个 Python 进程，最多 500 条；服务重启或 Console 配置签名变化后证据消失；
- `q<epoch>-<seq>` 与 `p<seq>` 仍暴露序号结构，proposal ID 在重启后重号；
- `QueryService` 没有显式 principal/session 上下文，同一实例中的所有调用共享 evidence；
- 建议卡只检查 query ID 是否在内存，不校验调用主体、会话、有效期、source、dataset version 或 result digest；
- query 日志只保存文本 `detail`，不保存规范化查询、脱敏结果摘要或可验证 digest；
- 建议卡仅复制 query ID/tool/target/at，后续无法展示生成当时的关键结果和完整 warnings；
- JSONL audit 可关闭、没有主体/会话字段，也没有数据库事务或不可变约束；
- `/api/gateway/queries/{query_id}` 和 `/api/gateway/proposals/{proposal_id}` 尚未实现；
- Vue 证据展开依赖本标签页 Pinia 内存中的完整结果，刷新或重启后无法解释已生成卡片；
- 现有错误只把所有引用失败归为 `query_expired`，不能稳定区分主体、会话、版本和 digest 冲突。

## 3. 冻结契约

### 3.1 证据上下文与信任边界

新增内部值对象：

```text
EvidenceContext
  principal
  session_id
  channel(console|mcp_stdio|mcp_http|demo)
```

规则固定为：

1. `principal/session_id` 由传输适配层注入 `QueryService`，不出现在 `query_*` 或 `propose_action` 的业务参数中；
2. v0.3 单凭据部署只映射一个逻辑主体，不保存 Token 原文或 Token hash：
   - Console 配置 Token：`console:configured`；未启用 Token 的本机/展厅：`console:local`；
   - MCP HTTP 配置 Token：`mcp:configured`；显式匿名展厅：`mcp:demo`；
   - MCP stdio：`mcp:local`；
3. v0.3 的 principal 是证据隔离域，不是 v0.4 多主体认证/RBAC；多 Token 映射、轮换、吊销和按主体限流仍留在 v0.4；
4. MCP stdio 以一次 ServerSession 生命周期为 session；MCP HTTP 以 FastMCP 的 stateful transport session 为 session；适配层为每个底层 session 对象分配不可预测的内部 session ID；
5. Console 使用请求头 `X-D2A-Session-ID`，Vue 首次加载以 Web Crypto 生成随机 ID，仅保存在当前标签页 `sessionStorage`，不进 URL、localStorage、日志或请求体；
6. Console gateway 路径缺少、格式非法的 session header 返回 `422 invalid_session`；其它既有 API 不因 M5 强制该 header；
7. session ID 只允许 `16–128` 个 URL-safe 字符，作为不透明标识使用；不能由用户名、时间戳、Token、IP 或递增序号构造；
8. 测试和内部调用必须显式提供 `EvidenceContext`；不得保留一个会把所有调用静默归到共享会话的生产默认值。

Console 或 MCP 的调用方即使在请求体中附加 `principal/session_id`，也必须按未知参数拒绝，不能覆盖传输层上下文。
Console 同一 tab 的 session header 可跨后端进程重启继续使用；MCP 连接重建后是新
ServerSession，必须获得新 session ID，不能引用旧连接的 query。旧 MCP query 仍保留供
持久审计和已生成 proposal snapshot 使用，不能因此开放跨会话引用。

### 3.2 不可预测 ID 与生命周期

query/proposal ID 使用 `secrets.token_urlsafe(24)` 级别的随机熵，并加稳定类型前缀：

```text
qry_<32 个 URL-safe 字符>
prp_<32 个 URL-safe 字符>
```

约束：

- 禁止时间戳、进程 epoch、计数器或 SQLite rowid 作为公开 ID；
- 数据库主键保证全局唯一；极小概率碰撞最多重试 3 次，仍冲突则安全失败；
- query evidence 默认引用有效期为创建后 24 小时；时钟与 TTL 通过依赖注入可测试；
- 到期只禁止创建新建议卡，不改写或删除已有 query 行；query 详情明确返回 `query_expired`；
- 已生成 proposal 不随 query 到期；其 evidence snapshot 仍可按原 principal/session 查看；
- M5 不做自动删除或后台 retention job，避免未经治理丢失审计；所有 JSON 字段和单卡 evidence 数量必须有界，长期归档策略留给真实运行反馈。

所有时间使用带时区 ISO 8601，比较统一转换为 UTC；不得使用本地无时区字符串决定过期。

### 3.3 规范化查询

只有实际返回已发布数据结果的调用产生可引用 query ID。对象/指标目录、未实现指标和失败调用的 `query_id` 继续为 `null`，但失败仍可写 audit。

`normalized_query` 保存服务端实际执行语义，而不是原始请求文本：

```json
// query_objects
{
  "tool": "query_objects",
  "source": "digiwin_e10",
  "object": "Customer",
  "filters": {"customer_no": "C001"},
  "order_by": "customer_no",
  "desc": false,
  "limit": 20
}

// query_metrics
{
  "tool": "query_metrics",
  "source": "digiwin_e10",
  "metric": "gross_margin_rate",
  "group_by": "月",
  "limit": 24
}
```

规则：

- filters 的键按 Unicode code point 排序，值保留 `null/string/number/bool` 类型；
- 保存 clamp 后的实际 limit、实际默认 group_by 和排序方向；
- 不保存 SQL、物理表名、模板磁盘路径、Token、HTTP header 或未采用的客户端参数；
- 使用 UTF-8、`sort_keys=True`、紧凑分隔符和 `allow_nan=False` 的 canonical JSON；
- 参数大小、字符串长度、filters 数量继续受对象属性和明确上限约束，超限在查询前返回 `422 invalid_params`。

### 3.4 result digest

digest 的输入是已完成服务端脱敏后的规范化结果 envelope：

```text
evidence_schema_version=1
+ tool / source / target
+ normalized_query
+ actual dataset_version / template_version / binding_hashes
+ response payload（排除 query_id、duration_ms、created_at 等易变 meta）
```

算法固定为：

```text
canonical JSON UTF-8 bytes → SHA-256 → "sha256:" + 64 位小写 hex
```

约束：

- digest 必须在敏感字段脱敏后计算；不能 hash 原始敏感值后把 hash 当作安全展示值；
- 字典键稳定排序，数组保留查询顺序，整数/布尔/null 保留 JSON 类型，禁止 NaN/Infinity；
- `duration_ms/query_id/session_id/principal/expires_at` 不进入 digest，避免同一结果因运行元数据变化而漂移；
- warnings 不进入结果 digest，但以独立快照完整进入 query/proposal evidence；
- 查询响应 `meta.result_digest` 与数据库记录必须来自同一已规范化 payload；
- proposal evidence 输入从 `[{claim, query_id}]` 升级为 `[{claim, query_id, result_digest}]`；服务端使用常量时间比较请求 digest 与持久记录；
- digest 缺失、格式非法或不一致均拒绝建议卡，不允许仅凭可猜到/获得的 query ID 引用结果。

M5 不把 digest 宣称为签名、MAC 或跨系统防篡改证明；它是同一服务内绑定“引用”和“查询结果”的完整性校验值。

### 3.5 result summary

`result_summary` 从同一个脱敏 canonical payload 派生，不能重新查当前数据：

```text
query_objects:
  kind / returned_row_count / columns
  rows_preview（稳定查询顺序，最多 20 行）
  preview_truncated

query_metrics:
  kind / metric / status / unit / group_by / returned_row_count
  series_preview（稳定查询顺序，最多 50 项）
  preview_truncated
```

规则：

- summary 只包含查询已经返回给调用方的脱敏值；不得回到 raw/object 表补取更多列；
- 单个 summary canonical JSON 上限 32 KiB，按完整行/项截断并显式设置 `preview_truncated=true`；
- `row_count=0` 仍生成可引用 evidence，summary 明确为空结果；
- 对象列顺序取 frozen template，指标序列顺序取实际响应；
- summary 不是完整结果快照；完整返回内容只由 `result_digest` 绑定；
- proposal 复制 summary、digest、normalized query、dataset version 和 warnings，之后禁止更新；
- GET query/proposal 只返回该有界 summary，不提供任意历史完整结果下载接口。

### 3.6 持久化模型

新增四张系统表。

`d2a_gateway_query_evidence`：

```text
query_id PK / evidence_schema_version
principal / session_id / channel / source
tool / target / normalized_query_json
dataset_version / template_version / binding_hashes_json
result_digest / result_summary_json / warnings_json / row_count
created_at / expires_at
```

`d2a_gateway_proposal`：

```text
proposal_id PK / evidence_schema_version
principal / session_id / channel / source
object / action / action_desc / tier / conclusion / governance
dataset_version
created_at
```

`d2a_gateway_proposal_evidence`：

```text
proposal_id / evidence_ordinal PK
claim / query_id
query_tool / query_target / normalized_query_json
dataset_version / template_version / binding_hashes_json
result_digest / result_summary_json / warnings_json
query_created_at
```

`d2a_gateway_audit`：

```text
event_id PK / created_at
principal / session_id / channel / source
operation / target / outcome / reason_code
query_id / proposal_id / dataset_version / result_digest
detail_json
```

数据库约束：

- query、proposal 和 proposal evidence 建 principal/session、created_at、dataset_version 查询索引；
- proposal evidence FK 指向 proposal，按 ordinal 稳定排序；不以 FK 依赖 query 行长期存在；
- query/proposal/proposal evidence/audit 均建立拒绝 UPDATE/DELETE 的 freeze trigger；
- proposal 成功时 proposal 主记录、全部 evidence snapshot 和成功 audit 在同一 `BEGIN IMMEDIATE` 事务提交；
- query 成功时 query evidence 与成功 audit 在同一事务提交；持久化失败则不返回可引用 query ID，并返回 `evidence_store_unavailable`；
- 不给 query evidence 建会随 dataset GC 级联删除的外键；历史数据集物理表清理后 summary/digest 仍是历史证据；
- migration 对新库、M4 旧库、重复初始化、只读 reopen 和并发初始化幂等；schema 未完成时查询 fail-closed，不回退内存日志；
- 审计 `detail_json` 只允许结构化、有界的安全字段，不保存结果行、claim、conclusion、SQL、Token、header、路径或 traceback。

既有 `audit_sink` 继续接收不含结果正文的兼容事件；SQLite `d2a_gateway_audit` 是 M5 的事实来源，不能通过 `--audit-log off` 关闭。

### 3.7 查询写证据顺序

业务数据仍只读，证据元数据允许写入同一个 landing SQLite：

```text
published_read_tx
  → 解析唯一 published snapshot
  → 执行对象/指标 SQL
  → 服务端脱敏并构造响应 payload
  → 关闭只读事务
  → 规范化查询/结果，生成 digest + summary
  → evidence write tx：query evidence + audit
  → 返回带 query_id/digest/summary/expires_at 的响应
```

约束：

- evidence 记录的 `dataset_version` 必须来自执行 SQL 的同一个 published read transaction；不得在写 evidence 时重新读取 current 指针；
- 并发 publish 时一次查询只能记录完整旧版本或完整新版本；
- evidence 写入不能修改 raw、objv、dataset/object version、lineage、quarantine 或水位；
- data query 成功但 evidence 写失败时，不返回未持久化结果伪装成可引用查询；错误审计尽力写入现有 sink，但不能伪造数据库成功记录；
- 调用取消、进程崩溃和 SQLite busy 不得留下只有 audit 没有 evidence 的“成功”事件；
- SQLite busy 使用现有有界 timeout，不进行无限重试。

### 3.8 建议卡验证与快照

建议卡创建按请求中的 evidence 顺序，在一个事务中执行：

1. 校验请求上限、query/proposal ID 和 digest 格式；
2. 按 query ID 读取全部 evidence；不存在或已过期则 `409 query_expired`；
3. principal 不一致返回 `403 evidence_principal_mismatch`，不返回目标 evidence 内容；
4. session 不一致返回 `409 evidence_session_mismatch`；M5 不提供跨会话授权旁路；
5. source 不一致返回 `409 evidence_source_mismatch`；
6. 使用常量时间比较客户端 `result_digest` 与持久 digest；不一致返回 `409 result_digest_mismatch`；
7. 所有被引 query 必须有非空且相同的 `dataset_version`；混用返回 `409 dataset_version_mismatch`，M5 不采用可忽略 warning 策略；
8. 校验持久 JSON、digest 格式和 schema version；无法安全解析返回 `409 evidence_integrity_failed`；
9. 从已校验 query 行复制 evidence snapshot，聚合所有 query-time warnings；
10. 原子写 proposal、evidence snapshots 和成功 audit 后返回建议卡。

任一步失败都不写 proposal；拒绝 audit 使用独立有界事务记录 reason code，不包含他人 evidence 内容。重复 query ID 可以被多个 claim 引用，但每项都必须提交正确 digest；同一卡最多 20 条 evidence，claim/conclusion 分别设置明确字符上限。

后续 dataset publish/rollback、模板修改、query 到期或服务重启都不能改写 proposal。建议卡只展示生成时证据，并明确其 dataset version；它不自动升级到当前版本。

### 3.9 API 与错误契约

查询成功的 `McpQueryMeta` 升级为：

```text
query_id
evidence_scope = "principal_session"
session_id
result_digest
result_summary
created_at / expires_at
+ 既有 tool/target/row_count/duration/masked_fields/warnings
+ dataset_version/template_version/binding_hashes
```

目录、未实现指标等不可引用响应的 query/digest/summary/created/expires 均为 `null`，不能返回半套证据字段。

新增只读 API：

```text
GET /api/gateway/queries/{query_id}
GET /api/gateway/proposals/{proposal_id}
```

两者均从认证/部署映射 principal，从 `X-D2A-Session-ID` 读取 session；只返回同 principal/session 的持久证据。proposal 响应中的每条 evidence 直接包含冻结的 query snapshot，不要求客户端再访问已经过期的 query。

`ProposalEvidenceInput` 增加必填 `result_digest`；`ProposalQueryRef` 扩展 normalized query、dataset/template/binding、digest、summary、warnings、created_at。`ProposalResponse` 增加 session/source/dataset version，保持既有 object/action/tier/conclusion/governance 字段。

稳定错误语义：

| HTTP | reason_code | 条件 |
| --- | --- | --- |
| 401 | `unauthorized` | 既有 Bearer 配置下认证失败 |
| 403 | `evidence_principal_mismatch` | query/proposal 属于其他主体 |
| 404 | `evidence_not_found` | detail API ID 不存在 |
| 409 | `query_expired` | query 已过期或 proposal 引用不存在 |
| 409 | `evidence_session_mismatch` | 当前 session 与证据 session 不同 |
| 409 | `evidence_source_mismatch` | proposal 混用其它 source |
| 409 | `dataset_version_mismatch` | 同一卡混用多个 dataset version |
| 409 | `result_digest_mismatch` | digest 缺失对应或比较失败 |
| 409 | `evidence_integrity_failed` | 持久证据 schema/JSON/digest 损坏 |
| 422 | `invalid_session` / `invalid_params` | session、ID、digest 或请求上限非法 |
| 500 | `evidence_store_unavailable` + `error_id` | migration/写入/读取内部失败 |

错误响应不返回其他 principal/session、数据库路径、SQL、Token、result summary、claim、conclusion 或 traceback。OpenAPI 明确声明 `X-D2A-Session-ID` header、所有响应模型和 reason code。

### 3.10 数据治理、有界性与兼容性

- digest 和 summary 只消费现有 MCP 脱敏响应，不建立 raw/lineage 解敏旁路；
- 敏感值不能因 hash 后可比对而出现在 summary、audit 或错误中；
- query detail 不是任意历史结果 API，只返回有界 summary；
- principal/session/query/proposal ID 是治理元数据，不在普通日志中输出完整值；诊断日志最多使用安全前缀；
- Console session ID 与 Token 一样只在当前 tab 的 `sessionStorage`，logout 同时清除；
- `/`、`/v0`、`/v1`、MCP stdio/HTTP、showroom、portable distribution 和已有查询参数保持可用；
- 现有调用方必须为 proposal evidence 补 `result_digest`，这是 v0.3 明确的契约升级；不保留“只有 query_id 也能创建卡片”的弱校验兼容路径；
- 进程内 `_query_log/_query_seq/_proposal_seq` 在持久实现接通后删除，不维护双写或回退；
- M5 不新增列表/搜索全部主体证据、任意跨会话复用、历史完整结果导出或在线删除入口。

## 5. 前端交互

MCP Lab 保持现有对象查询、指标查询、建议卡三块布局，增加证据身份与持久详情：

1. 标签页首次进入生成 `d2a_evidence_session_id`，API client 对 gateway query/proposal 路径自动发送 header；
2. 查询结果显示 query ID 短摘要、dataset version、digest 短摘要、有效期和 `principal_session` badge；
3. “加入 evidence”同时保存 query ID 与完整 digest，用户只编辑 claim；
4. 建议卡生成后展示统一 dataset version、query-time warnings 和每条冻结 summary；
5. 展开 evidence 直接读取 proposal response 的 snapshot；不再从本地 history 找完整结果；
6. 通过 query/proposal ID 访问详情时调用新增 GET API，并清楚显示过期、会话不一致和 digest/integrity 错误；
7. 页面刷新后同一 tab/session 可读取持久详情；关闭 tab 后 sessionStorage 清除，新会话不能继续引用旧 query；
8. logout 清空 Token、session ID、Pinia 查询历史、proposal 和已展开 summary。

状态覆盖：

```text
idle / loading / success / empty result / expired
principal mismatch / session mismatch / source mismatch / dataset mismatch
digest mismatch / integrity failed / unauthorized / unavailable / unknown error
```

Mock 至少覆盖对象/指标摘要、空结果、summary 截断、混合 warnings、过期 query、跨会话、digest mismatch、持久 proposal、未知错误。Mock/Real 继续使用同一生成类型。

## 7. 测试矩阵

### 7.1 canonical result、digest 与 summary

- 同语义 filters 不同输入键序得到相同 normalized query/digest；数组顺序变化可检测；
- string/int/float/bool/null 类型不混淆，NaN/Infinity 和超限字符串 fail-closed；
- query ID、耗时、创建时间变化不影响同结果 digest；数据、版本、条件、排序或 limit 变化影响 digest；
- 对象敏感字段在 digest/summary 之前已经为遮罩，原值不出现在 SQLite、JSONL、API 或错误；
- 对象 0/1/20/21/200 行与指标 0/1/50/51 项的截断边界稳定；
- 32 KiB 上限按完整条目截断，重复执行 summary bytes 完全一致；
- warnings 与 summary 独立持久并完整快照，warning 变化不被旧 proposal 改写。

### 7.2 存储、ID 与生命周期

- 新库、M4 库、部分迁移库、重复初始化、并发初始化和只读 reopen；
- query/proposal ID 格式、随机性、并发唯一、碰撞重试和重启不重号；
- query+audit、proposal+snapshots+audit 各自全成或全败；
- freeze trigger 拒绝 UPDATE/DELETE；索引按 principal/session/ID 命中；
- 过期边界使用注入时钟精确测试；过期 query 不能新建卡但旧 proposal 可读；
- service restart 后，显式复用同一 Console tab session 可在 TTL 内创建建议卡并读取详情；MCP 重连后不能引用旧 session query；
- dataset GC 不删除 query/proposal snapshot；旧 dataset 物理表不存在时详情仍可读。

### 7.3 principal/session 与拒绝路径

- 同 principal + 同 session + 正确 digest 成功；
- principal 不同为 403，响应/audit 不含目标 summary；
- session 不同为 409，M5 不存在跨会话授权开关；
- Console body、MCP tool args 中夹带 principal/session 被当未知参数拒绝；
- MCP 两个 ServerSession 不能互引；同一 ServerSession 连续工具调用可以引用；
- Console 两个 tab sessionStorage ID 不互引，刷新不换 ID，关闭/新 tab 生成新 ID；
- Token 未启用的本机/展厅映射固定 local/demo principal，但仍执行 session 隔离；
- header 缺失、过短、超长、非法字符和日志泄漏测试通过。

### 7.4 proposal 与版本完整性

- digest 缺失、格式非法、单字符篡改和属于另一个 query 均失败；
- 不存在/过期 query、重复 query、多 evidence 顺序和 20/21 条边界；
- 同 dataset 不同对象/指标可以组合；不同 dataset/source 必须拒绝；
- proposal evidence 保留 normalized query、actual dataset/template/binding、summary、warnings 和 query time；
- publish/rollback 后旧 proposal 内容逐字节不变，页面明确显示旧 dataset version；
- 人工构造损坏 JSON、未知 schema version、非法 digest 时 fail-closed 并写 integrity audit；
- proposal 事务中任一 snapshot/audit 写失败不留主记录或部分 evidence。

### 7.5 API、前端与 E2E

- POST query/proposal 与两个 GET detail 的 200/401/403/404/409/422/500 契约；
- OpenAPI 的 header、nullable evidence 字段、reason code 与生成 TypeScript 一致；
- MCP tool schema 不出现内部 Context/principal/session，stdio/HTTP 行为一致；
- MCP Lab 查询→选择 evidence→生成卡→展开冻结 summary 的真实链路；
- 页面刷新后 detail 可恢复，query 过期后 proposal snapshot 仍显示；
- session/digest/dataset 错误有稳定中文提示且不清掉仍有效的其它查询；
- Mock 空结果/截断/warnings 与 Real 布局一致；窄屏、键盘和 loading/retry 可用；
- `/`、`/v0`、`/v1`、M4 lineage、M3 preview、showroom 接单评审与 portable bundle 无回归。

## 9. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 请求体伪造 principal/session | 仅传输适配层构造 `EvidenceContext`；工具/API body 额外字段拒绝 |
| HTTP/stdio 会话被错误合并 | MCP 按底层 ServerSession 分配随机 ID；Console 每 tab 随机 header；双会话集成测试 |
| digest 算到脱敏前值，形成敏感值比对旁路 | 只接受最终响应 payload；测试扫描 SQLite/JSONL/API 不出现原值 |
| digest 因耗时/ID 漂移而不稳定 | 明确排除易变 meta；canonical bytes 黄金测试 |
| summary 变成完整历史数据仓库 | 行/项和 32 KiB 双上限；只存脱敏响应子集；无完整结果 detail API |
| data query 成功但 evidence 没落库 | evidence+audit persist-or-fail，返回前回读/事务确认；不回退内存 qlog |
| proposal 在多条 evidence 中途失败留下半卡 | 单个 `BEGIN IMMEDIATE` 写主记录、全部快照与 audit |
| 并发 publish 记录错误版本 | 从执行 SQL 的 published read transaction 携出 version；写证据时不重读 current |
| 数据变化后旧卡悄悄展示新结果 | proposal 复制 summary/digest/warnings/version；不可变触发器；UI 标注生成时版本 |
| 不同 dataset 的数字被拼成一张卡 | v0.3 固定 fail-closed，不提供忽略 warning 的旁路 |
| SQLite 证据无限增大 | 单条强上限、M5 无原始全量结果；先观测规模，保留策略需单独治理后实施 |
| M5 滑向多主体认证项目 | principal 仅固定部署映射；Token 轮换、多凭据/RBAC/按主体限流明确留在 v0.4 |

## 10. 明确非目标

- 不解析自然语言 claim，不逐个验证 claim 中数字或结论逻辑；
- 不实现数字/字段级 citation anchor、签名、MAC、外部时间戳或防恶意数据库管理员篡改；
- 不实现跨会话授权复用；v0.3 对 session mismatch 一律拒绝；
- 不实现多 Token 主体目录、Token 轮换/吊销、RBAC、租户、按主体限流或 TLS；
- 不保存未脱敏完整查询结果，不提供全局 evidence 搜索、导出或管理页面；
- 不自动删除 query/proposal/audit，不在 M5 引入后台 retention/归档任务；
- 不修改对象/指标业务查询能力，不新增任意 SQL、聚合语言、分页游标或写回；
- 不提前实现 M6 validation run、v0.3 发布报告或 v0.4 批次 receipt/schema fingerprint；
- 不改变 M4 lineage、M3 Preview、M2 publish/rollback 的事实来源和事务边界。
