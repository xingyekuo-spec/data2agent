# data2agent 产品开发路线图：从可运行到可观察、可验证、可试点

> 状态：执行基线 v1.1
> 日期：2026-07-18
> 适用范围：`data2agent` v0.1.6 之后的产品开发
> 建议周期：11–14 周（按 1–2 名开发人员估算；按里程碑验收，不按自然周强行截断）
> 关联文档：[产品总览](../../design/00-overview.md) · [抽取框架](../../design/02-extraction.md) · [MCP 网关](../../design/03-mcp-gateway.md) · [控制台设计](../../design/05-console.md) · [Vue Console 实施规格](../specs/2026-07-15-console-ui-design.md)

## 1. 文档目的

当前项目已经具备抽取、推送、落地、映射、隔离、MCP 查询、管理界面和便携部署等能力，但大量能力只能通过命令行、SQLite 内部表和日志间接验证。用户难以回答以下问题：

- 当前整条链路是否正常；
- 一次同步具体处理了什么；
- 某个对象字段来自哪张表、哪一列和哪条转换规则；
- 为什么一行数据被隔离或触发熔断；
- MCP 建议卡中的数字是否确实来自某次查询；
- 前端展示的是模拟结果、演示结果还是真实生产状态。

后续开发的首要目标不是继续扩大后端功能面，而是先建立**可观察、可验证、可验收**的产品闭环，再补齐影响现场正确性和安全性的生产能力。

本路线图用于：

1. 统一未来三个版本的产品目标和边界；
2. 指导前端先行和后端逐项接入；
3. 为每个阶段定义可客观判断的验收门槛；
4. 防止功能扩散到多租户、ERP 写回等当前非目标；
5. 作为后续详细技术设计和实施计划的上层依据。

## 2. 总体目标

一句话目标：

> 把 data2agent 从“后端能力已经存在，但难以验证”，推进到“用户能看见每一步输入、输出、规则和异常，并能独立完成一次验收”。

目标产品链路：

```text
ERP / Excel
    ↓
抽取 → 推送 → Raw 落地 → 映射 → 对象层 → MCP → 建议卡
 │      │        │         │       │       │       │
状态   批次回执   数据抽样   规则血缘 版本    查询证据 结果证据
```

开发顺序统一为：

```text
接口契约
  → Mock 场景
  → 前端可见
  → 接入真实后端
  → 自动测试
  → 页面验收
  → 便携包验证
```

## 3. 产品原则

### 3.1 前端先行，但不伪造后端完成度

- 前端可以先基于 fixture/mock 完整开发；
- 页面必须显著标识 `MOCK`、`DEMO` 或 `REAL`；
- 后端暂时无法提供的状态显示“尚不可检测”，不能显示为正常；
- 请求失败不能被转换成零数据或空列表后继续显示绿色状态；
- 每个页面必须覆盖正常、空数据、运行中、警告、失败和不可达状态。

### 3.2 契约先于实现

- 管理 API 全部使用 Pydantic request/response model；
- 提交 OpenAPI 快照并生成 TypeScript 类型；
- CI 比对后端实时 OpenAPI 与仓库快照，发现接口漂移即失败；
- 前端不得直接读取 SQLite，也不得解析自由文本日志作为核心状态来源；
- 保留现有 API 兼容性，新字段优先以向后兼容方式增加。

### 3.3 可观察不等于可修改

第一阶段优先提供只读观察、预览和验证。以下能力在具备预览、审计与回滚前不得开放：

- 在线修改生产 binding；
- 自动将 binding 从 `draft` 置为 `verified`；
- 删除 raw 或隔离数据；
- 绕过错峰窗口强制抽取；
- 写回 ERP；
- 无预览直接发布映射。

### 3.4 两套界面分工不变

| 界面 | 定位 | 后续策略 |
| --- | --- | --- |
| Jinja2 + HTMX 管理页 | 首次安装、配置、日志、故障恢复 | 保留，继续作为便携包应急入口 |
| Vue Console | 日常监控、数据验证、隔离复核、MCP 调试 | 从“远期规划”升级为主产品界面 |

Vue Console 固定挂载在 `/v1`；现有 `/` 管理页和 `/v0` 简版页保持可用，直到便携包分发和现场验证稳定后再重新评估。

## 4. 版本路线

| 版本 | 建议周期 | 核心目标 | 发布门槛 |
| --- | ---: | --- | --- |
| v0.2 可观察 | 5–6 周 | 让整条链路、运行、数据、隔离和 MCP 状态可见 | 用户无需查看数据库即可定位链路状态 |
| v0.3 可验证 | 3–4 周 | 让字段血缘、映射、对象版本和查询证据可验证 | 任意关键结果能追溯到输入和规则 |
| v0.4 可试点 | 3–4 周 | 补齐跨机一致性与安全,并在试点负载下验证 v0.3 发布机制 | 满足真实工厂连续运行与验收要求 |

版本号代表产品里程碑，不要求严格按自然周发布。表中周期是 1–2 人的估算区间,不是截止日;
任一里程碑未通过就继续修复,不能为了维持周数而“有条件通过”。若版本发布门槛未满足,
不进入下一版本的高风险写操作开发。

## 5. v0.2：可观察控制台

### 5.1 版本目标

解决“发生了什么、哪里失败、当前使用什么数据”的问题。此版本不追求在线编辑复杂规则。

### 5.2 里程碑 1：API 契约基线

该里程碑先固定前后端边界,不要求同时完成 Vue 页面。建议作为独立合并门禁。

#### 交付物

- 盘点现有管理 API,为全部端点增加 Pydantic request/response model；
- 统一错误模型、动作语义、分页和带时区时间字段；
- 导出并提交 `console-ui/openapi.json`；
- 建立从后端代码重新导出 OpenAPI 的漂移 CI；
- 明确 v0.2 新端点的 schema,未实现端点可以先有契约和 fixture,但不能返回伪造成功。

#### 验收标准

- OpenAPI 不再产生核心响应 `unknown`；
- 后端契约变化但未更新快照时 CI 失败；
- 当前 Jinja/v0 API 行为保持兼容；
- 错误不会被定义为正常空结果。

### 5.3 里程碑 2：Vue 工程骨架与 Mock

#### 交付物

- 新建独立 `console-ui/`：Vue 3、Vite、TypeScript、Element Plus、Pinia、Vue Router；
- 建立统一布局、导航、状态颜色、空状态、错误状态和加载状态；
- 使用 `openapi-typescript` 生成类型,统一使用 `openapi-fetch`；
- 建立 mock/fixture 层与 `MOCK / DEMO / REAL` 模式；
- 建立 TypeScript 类型检查、前端构建和基础组件测试；
- 页面顶栏持续展示环境模式。

#### 必备 Mock 场景

1. 全链路正常；
2. 首次安装、没有数据；
3. 同步运行中；
4. 推送失败；
5. apply 熔断、对象层继续使用旧版本；
6. 部分服务不可达；
7. 存在未处理隔离；
8. binding 或指标仍为 draft；
9. Token 无效；
10. API 返回未知错误。

#### 验收标准

- 后端不启动时，前端可以通过 Mock 完整演示；
- Mock 与 real 使用同一生成类型和领域组件；
- TypeScript 不使用 `any` 绕过核心 API 类型；
- 每个基础页面状态可以区分未加载、空数据、失败和正常；
- 所有 Mock 页面均显示非生产标志,生产构建不得默认启用 Mock。

### 5.4 里程碑 3：产品总览与管道状态

#### 页面能力

- 产品总览 Dashboard；
- 服务健康状态；
- 全链路管道图；
- 最近运行；
- 当前告警；
- raw、对象层、隔离区数据量概览；
- 模板版本、应用版本、数据更新时间；
- 当前数据是否为旧对象版本。

管道节点：

```text
ERP → 抽取 → 推送 → Raw → 映射 → 对象层 → MCP
```

每个节点至少显示：

- `unknown / idle / running / healthy / warning / failed / stale` 状态；
- 最近成功和最近失败时间；
- 本次输入、输出数量；
- 本次耗时；
- 错误摘要；
- 数据或组件版本；
- 详情入口。

#### 验收标准

- 用户能在 30 秒内判断整条链是否健康；
- 任一失败能定位到具体节点；
- 明确区分“从未执行”“正在执行”“成功”“失败”“使用旧版本”；
- 无法检测的节点显示 `unknown`，不得默认为绿色；
- 总览中的数量口径有说明，例如对象层行数不等于 raw 行数。

### 5.5 里程碑 4：运行记录与数据浏览

#### 页面能力

- 同步、apply、reconcile 运行列表；
- 单次运行详情；
- 表级策略和水位变化；
- 批次记录；
- SQL 审计列表；
- raw 表只读浏览；
- 对象层只读浏览；
- 按业务键搜索；
- 原始 JSON 响应查看；
- 分页、筛选和返回数量限制。

建议统一运行模型：

```text
Run
 ├─ type: sync | apply | reconcile | ingest
 │         # v0.3 起增加 validation,继续使用同一 Run/steps 模型
 ├─ status: running | ok | paused | failed | aborted
 ├─ started_at / finished_at / duration_ms
 ├─ source / dataset_version
 └─ steps[]
      ├─ table/object/batch
      ├─ rows_in / rows_out / quarantined
      ├─ watermark_before / watermark_after
      └─ error
```

#### 验收标准

- 可以回答一次同步读取了哪些表、多少行以及水位如何变化；
- raw 和对象层均可查看真实样本；
- 数据浏览默认分页，服务端强制 limit 上限；
- 敏感字段和脱敏状态有明显标识；
- SQL 审计支持按源、动作和时间筛选；
- UI 不依赖解析日志文本来判断运行是否成功。

### 5.6 里程碑 5：隔离与模板

#### 页面能力

- 隔离区按对象分组；
- 原始值、业务键、失败原因、批次和时间；
- 隔离率与熔断阈值；
- 对象是否继续使用上一稳定版本；
- 模板对象列表；
- binding 的 `draft / verified / disabled` 状态；
- 字段映射、枚举 map 和 derived 规则只读展示；

#### 本阶段非目标

- 在线编辑或发布 mapping；
- 单行隔离重试；
- 自动修复数据；
- 自动将 binding 置为 `verified`。

#### 验收标准

- 可以看见隔离行、原始值和失败原因；
- 可以明确看见 binding 和指标是否经过现场校准；
- 对象级重试按钮必须提示“会重新映射整个对象”。

### 5.7 里程碑 6：MCP Lab

#### 页面能力

- MCP 对象查询；
- MCP 指标查询；
- 建议卡生成；
- query ID 和 evidence 展示；
- 原始 MCP JSON、脱敏字段、口径警示和 dataset version 查看；
- Jinja 调试端点保持只读,建议卡使用独立 gateway 端点。

#### 验收标准

- 用户可以独立执行一次 MCP 查询并查看完整响应；
- 建议卡每条 evidence 可展开到关联查询；
- 当前 query ID 的进程级边界有明确提示,不伪装成 v0.3 强证据；
- MCP Lab 不能绕过敏感字段脱敏和治理档位。

### 5.8 v0.2 发布门槛

- 八个主页面可用：总览、管道、运行、审计、数据、隔离、模板、MCP Lab；
- Settings 在 v0.2 只读展示 `/api/config` 的非敏感配置,不计入八个主页面的功能验收；
- 所有页面均有 Mock 和真实 API 模式；
- 现有 Jinja 管理页不回归；
- 前端构建不依赖运行时 CDN；
- Docker、源码开发模式和便携包策略均有验证说明；
- Vue 固定挂载 `/v1`;dist 缺失时 `/v1` 明确提示未安装,不得静默回落为 Jinja/v0；
- 用户不查看 SQLite 内部表即可完成一次基本链路诊断。

## 6. v0.3：可验证数据链

### 6.1 版本目标

v0.2 回答“发生了什么”，v0.3 回答“为什么得到这个结果”。

### 6.2 字段级数据血缘

对象详情增加字段血缘接口和视图：

```text
SalesOrder.state = 已结案
    ← derived：CLOSE_STATE == C
    ← raw_digiwin_e10__SALES_ORDER.CLOSE_STATE = C
    ← 源记录 Id = 12345
    ← 抽取批次 abc123
```

每个字段至少包含：

- 对象名和业务键；
- 属性名和最终值；
- 源表、源列和源业务键；
- join 关系；
- map 前值和 map 后值；
- derived 命中规则；
- 抽取批次和映射批次；
- binding 状态与模板版本；
- 无法追溯时的明确原因。

验收标准：任取一个关键对象字段，可以在三次点击内追溯到 raw 记录和规则。

### 6.3 映射预览

新增隔离于正式 apply 之外的 preview 能力：

- 选择对象和样本范围；
- 使用当前 binding 或临时草稿执行映射；
- 显示成功、隔离和失败原因；
- 展示枚举未覆盖值；
- 展示业务键缺失/重复；
- 展示 derived 规则覆盖率；
- 展示修改前后 diff；
- preview 不写正式 `obj_*` 和正式隔离区。

验收标准：修改规则前可复现问题，修改规则后可确认问题是否解决，且不影响生产对象表。

### 6.4 数据集版本和原子发布

引入以下概念：

- `dataset_version`；
- `template_version`；
- `binding_hash`；
- 每个对象的 `object_version`；
- 当前稳定版本和待发布版本；
- 发布时间与发布结果。

对象表发布改为影子构建：

```text
构建 obj_X__new
  → 完整校验
  → 短事务原子切换
  → 记录版本
  → 保留上一稳定版本用于回滚
```

验收标准：

- MCP 不会读取空表或半构建数据；
- 熔断后继续服务上一稳定版本；
- 页面明确显示“raw 已更新、对象层仍为旧版本”；
- 关键对象可以作为一个数据集统一发布，避免跨对象版本混用。

### 6.5 MCP 证据模型升级

当前进程级 query ID 升级为：

```text
principal + session_id + query_id
+ normalized_query
+ result_digest / result_summary
+ created_at / expires_at
```

规则：

- 建议卡只能引用同一主体、同一会话内允许的查询；
- query ID 使用不可预测标识，不使用重启后复位的简单序号；
- evidence 保存必要的结果摘要，而不只保存查询描述；
- 审计记录主体、会话、工具、目标、查询时间和结果摘要；
- 不在审计日志中写入被脱敏的敏感原值。

验收标准：不同会话无法互相引用证据，建议卡可以展示生成当时的结果摘要。

### 6.6 一键验收报告

新增只读的“运行验收”流程，自动检查：

1. 服务可达；
2. ERP 连接；
3. 只读账号和白名单；
4. 同步执行；
5. 推送和落地；
6. raw 数据存在；
7. apply 和对象层；
8. 隔离率与熔断；
9. MCP 查询；
10. 脱敏；
11. evidence；
12. binding/指标草稿项；
13. 应用、模板和数据集版本一致性。

输出：页面报告 + 可下载 JSON；HTML/PDF 报告按真实交付需要再决定。

验收标准：实施人员可以从界面启动验收，并得到每项通过、警告、失败及证据链接。

### 6.7 v0.3 发布门槛

- 关键对象字段具备字段级血缘；
- 映射 preview 与正式 apply 隔离；
- 对象层原子发布并记录版本；
- MCP evidence 按身份和会话隔离；
- 一键验收覆盖完整演示链；
- 接单评审建议卡中的关键数字能够追溯到查询结果摘要。

## 7. v0.4：生产试点可靠性

### 7.1 版本目标

补齐跨机推送路径上的数据正确性、安全和运行可靠性，使产品具备真实工厂试点条件。

### 7.2 端到端批次提交协议

每个推送批次增加：

- 不可重复的 batch ID；
- source、table；
- 应用版本和模板版本；
- schema fingerprint；
- 行数；
- 内容摘要；
- 中间机发送时间；
- 平台落地提交时间；
- commit receipt；
- 重试次数和最终状态。

协议要求：

- 平台在数据库事务提交后才返回 receipt；
- 中间机保存有效 receipt 后才允许推进水位；
- 重推同一批次必须幂等；
- schema 不兼容时明确拒绝，不能静默丢列；
- 控制台可以查看缺失、重复、失败和摘要不一致的批次；
- 支持经过确认的批次重放。

### 7.3 E6b 跨机对账

完成纯出站拓扑的对账闭环：

```text
中间机计算源侧分段统计
  → 平台比对落地侧统计
  → 返回不一致段
  → 中间机重抽不一致段
  → 平台 upsert 并按主键全集标记软删
```

同时定义强制 deep 策略，初始建议：

- 最近三个月：每周 deep；
- 全历史：每月 deep；
- 金额、成本和订单状态相关关键表：按现场风险提高频率；
- 所有周期均可配置并在控制台展示下一次执行时间。

### 7.4 安全加固

试点前至少完成：

- 生产模式禁止明文 HTTP，强制 HTTPS，优先支持 mTLS；
- ingest、console、MCP 使用不同凭据；
- Token 可轮换、可吊销；
- Vue Console Token 仅保存在 `sessionStorage`,关闭标签页即清除,不得持久化到 `localStorage`；
- 查询审计包含调用主体；
- 按主体限流；
- raw 目录权限最小化；
- 数据盘和备份加密说明；
- raw 数据保留期和清理策略；
- 平台外网出口白名单；
- 明确推送前敏感列裁剪或令牌化策略；
- Token 和敏感值不得进入 URL、普通日志和页面源码。

### 7.5 SQLite 生产边界验证

形成可复现压测和明确换库阈值：

- 最大 raw 行数和数据库文件大小；
- 每分钟 ingest 批次数；
- apply 全量重建时间；
- ingest、apply、console 与 MCP 并发；
- P50/P95 MCP 查询延迟；
- WAL checkpoint 行为；
- 在线备份与恢复时间；
- 本地磁盘约束，禁止将 SQLite 放在网络共享盘。

当测试超过已定义阈值时再启动 PostgreSQL 切片，不在 v0.4 内提前建设完整多租户数据库架构。

### 7.6 真实工厂试点

试点验收清单：

- E10 表和字段字典核对；
- binding 从 `draft` 置为 `verified`；
- 枚举和状态码全集检查；
- 水位字段语义、时区和精度确认；
- 业务键唯一性验证；
- 接单评审指标口径确认；
- 允许窗口和限流取得工厂 IT 确认；
- 连续运行至少一周；
- 模拟网络中断、服务重启、坏数据和 schema 漂移；
- 工厂 IT 在不直接操作数据库的情况下完成一次诊断和恢复；
- `quote_response_hours` 完成真实数据基线实测并记录口径、样本范围和 caveats；
- 接单评审卡通过老板测试:非技术用户能在 30 秒内看懂结论、关键依据和口径警示；
- 输出最终验收报告和剩余风险清单。

### 7.7 v0.4 发布门槛

- 推送批次具备端到端 receipt 和校验摘要；
- E6b 可发现并修复删除和静默修改；
- v0.3 原子发布在试点负载下仍无读空窗,跨对象版本一致,并能回滚上一稳定版本；
- 生产路径使用加密传输；
- 已完成 SQLite 容量与并发基线；
- 真实工厂连续运行一周，无未解释的数据丢失和水位漂移。

### 8.4 通用响应要求

所有列表：

- 服务端分页；
- 明确 `total / limit / offset` 或 cursor；
- 稳定排序；
- limit 上限；
- 可选筛选条件进入 OpenAPI。

所有时间：

- 后端返回带时区 ISO 8601；
- 页面按浏览器时区展示；
- 原始值可在详情中查看；
- 不允许混用无时区字符串。

所有动作：

| HTTP/响应 | 含义 |
| --- | --- |
| `200 executed=true` | 动作已执行 |
| `200 executed=false` | 策略性跳过，例如窗口外 |
| `202` | 已进入异步执行队列，返回 run ID |
| `401/403` | 未认证或无权限 |
| `409` | 运行冲突、只读模式、熔断或版本冲突 |
| `422` | 请求参数错误 |
| `500` | 未处理异常，必须返回可用于日志关联的 error ID |

## 13. 产品成功指标

开发完成度不以页面或接口数量衡量，采用以下产品指标：

- 用户在 30 秒内判断链路是否健康；
- 用户在 3 分钟内定位失败节点；
- 任意关键对象字段在三次点击内追溯到 raw 和转换规则；
- 任意建议卡依据可追溯到查询结果摘要；
- 工厂 IT 不查看数据库即可完成同步验收；
- Mock 替换成真实接口时无需修改页面领域模型；
- 连续运行一周无未解释的数据丢失或水位漂移；
- `quote_response_hours` 有真实数据基线、可复核口径和 caveats；
- 非技术老板能在 30 秒内看懂接单评审卡的结论、依据与警示；
- 所有 draft、stale、unknown 和旧版本状态均不会被显示为正常。

## 14. 风险与控制措施

| 风险 | 表现 | 控制措施 |
| --- | --- | --- |
| 前端做成静态演示 | 页面漂亮但无法接真实接口 | OpenAPI 契约、漂移 CI、每阶段真实链路接入 |
| 前端复制后端逻辑 | 状态口径在两端漂移 | 后端输出领域状态，前端只负责展示 |
| Mock 被误认为真实 | 验收结论失真 | 全局环境标识、Mock 水印、禁止生产构建默认 Mock |
| 继续扩展功能面 | 可验证性长期无法完成 | 执行 P0/P1/P2 和明确非目标 |
| SQLite 并发问题晚暴露 | 现场出现锁等待或空窗 | v0.3 原子发布，v0.4 压测和换库阈值 |
| 跨机推送水位提前 | 数据丢失后难以发现 | receipt 后推进水位，完成 E6b |
| MCP 证据跨会话混用 | 审计和建议卡证据不可信 | 主体、会话和不可预测 query ID |
| Vue 破坏便携部署 | 现场无法打开主界面 | 保留 Jinja，dist 随 release/便携包分发 |

## 15. 开发节奏建议

每个里程碑使用一个可演示的纵向切片；小里程碑可在一周内完成,较大的数据浏览或 MCP Lab
允许跨周,以验收结果而非自然周结束为准：

1. 里程碑开始时冻结本次接口与 fixture；
2. 前端先用 Mock 完成全部页面状态；
3. 后端接入真实数据；
4. 增加自动测试；
5. 合并前用 SQLite 演示链和 Docker MSSQL 展厅链验收；
6. 记录未完成项和风险，不用“基本完成”替代失败状态。

每个版本结束安排一次发布门槛评审，只回答三类结果：

- **通过**：所有门槛满足，可以进入下一版本；
- **有条件通过**：仅剩不属于本版本发布门槛、且不影响数据正确性/安全性的低风险问题;
  任何未满足的发布门槛都不能通过改名或延期备注变成“有条件通过”；
- **不通过**：继续修复，不以新增功能掩盖未完成项。

## 16. 第一批实施任务

路线图批准后，按以下顺序生成详细实施计划：

1. **API 契约基线**：盘点现有 `/api/*`，补 response model、错误模型和 OpenAPI 快照；
2. **Vue 工程骨架**：创建 `console-ui/`、路由、布局、主题、API 客户端和 Mock 切换；
3. **全状态 fixture**：覆盖首次安装、正常、运行中、推送失败、熔断、旧版本和服务不可达；
4. **总览纵向切片**：`GET /api/overview|pipeline|services` → Mock 页面 → 真实页面 → 测试；
5. **运行纵向切片**：标准化 run model → 列表 → 详情 → 表/批次详情；
6. **数据纵向切片**：raw/object 安全分页浏览与业务键搜索；
7. **隔离与模板纵向切片**：只读展示、筛选、对象级重试提示；
8. **MCP 调试纵向切片**：查询、指标、建议卡和 evidence 展示；
9. **v0.2 集成验收**：本机、Docker、便携包三种路径；
10. 通过 v0.2 发布门槛后，再生成 v0.3 字段血缘和 dataset version 的详细技术设计。

第一批开发不得同时启动在线 mapping 编辑、E6b、多租户或 PostgreSQL 改造；这些任务会分散 v0.2 的验收目标。

## 17. 决策记录

本路线图确立以下产品决策：

1. Vue Console 从远期能力升级为当前主产品路线；
2. Jinja 管理页继续作为安装配置和故障恢复入口；
3. 前端允许 Mock 先行，但不允许隐瞒 Mock 或未知状态；
4. v0.2 以只读观察和调试为主，不开放高风险编辑；
5. v0.3 完成可验证闭环后，才进入生产可靠性建设；
6. E6b、批次 receipt 和加密传输是 v0.4 现场试点门槛，不是普通优化项；
7. 当前不以扩充对象、连接器或写回能力作为主要进度指标。
